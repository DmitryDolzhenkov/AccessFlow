# AccessFlow
Небольшая внутренняя система обработки заявок на доступ к корпоративным системам.

## Локальный запуск

1. Скопировать `.env.example` в `.env` и задать `POSTGRES_PASSWORD`.
2. `docker compose up -d` — PostgreSQL на `127.0.0.1:5432`, пользователь `devuser`.
3. Задать строку подключения в user-secrets (пароль в двойных кавычках, если в нём есть `;`):

   ```sh
   dotnet user-secrets set --project src/AccessFlow.Api "ConnectionStrings:AccessFlow" 'Host=localhost;Port=5432;Database=accessflow;Username=devuser;Password="<пароль>"'
   ```

4. `dotnet run --project src/AccessFlow.Api` — база `accessflow` создаётся, миграции применяются при старте.
5. `dotnet run --project src/AccessFlow.SystemStub` — заглушка System на `http://localhost:5199`: принимает вызовы Provisioning по URL из seed-данных и всегда выдаёт доступ. Без неё одобренные заявки остаются в Approved.

Тесты (`dotnet test`) поднимают собственный PostgreSQL через Testcontainers; нужен только запущенный Docker.

## Как ведётся разработка (AI-assisted flow)

Проект развивается с агентом Claude Code по повторяемому процессу: от постановки задачи до небольших проверяемых PR.

### Артефакты и источники истины

| Файл | Что содержит | Как появляется |
|---|---|---|
| `docs/problem.md` | Бизнес-проблема, AS-IS / TO-BE, черновой scope | Пишет человек |
| `GLOSSARY.md` | Единый язык домена: термины, определения, нежелательные синонимы. Без деталей реализации | `/grill-with-docs`, по ходу обсуждения |
| `docs/adr/NNNN-*.md` | Решения, которые трудно отменить, неочевидны без контекста и выбраны из реальных альтернатив | `/grill-with-docs`, только когда выполнены все три условия |
| `docs/prd.md` | Пронумерованные бизнес-правила `BR-NN`, API, что вне scope, допущения `A-NN` | Синтез согласованной модели (`/to-spec`) |
| GitHub Issues | Вертикальные срезы с критериями приёмки, ссылающимися на `BR-NN`, и зависимостями между issues | Нарезка PRD (`/to-tickets`) |
| `AGENTS.md` | Правила для агента: приоритет источников, архитектурные ограничения, команды, правила веток и PR | Пишет человек, дополняется по опыту |
| `docs/progress.md` | Статус каждого issue | Обновляется после каждого issue |

При конфликте приоритет такой: текущий issue → PRD → ADR → тесты → код.

### Шаг 1. Постановка: `docs/problem.md`

Свободным текстом описываются проблема, текущий и целевой процесс, а также явный список того, что **не** делаем. Явные «нет» так же ценны, как «да».

### Шаг 2. Доменная модель: `/grill-with-docs`

Агент задаёт вопросы **раундами**. В раунд входят все решения, которые уже можно принять, потому что от них ничего не зависит. На каждый вопрос агент даёт свою рекомендацию, вы отвечаете коротко: «Q1 a, Q2 ok…».

- Факты (что есть в коде и окружении) агент выясняет сам, решения принимает человек.
- Каждый согласованный термин сразу попадает в `GLOSSARY.md`. Размытые слова заменяются точными: например, «Employee» превращается в Requester и Beneficiary, а «Approver» — в System Owner.
- Агент проверяет модель на пограничных сценариях: самосогласование, дубли заявок, одновременные действия, смена владельца системы.
- ADR пишется только для решений, которые трудно отменить, неочевидны без контекста и выбраны из реальных альтернатив. В этом проекте так появились ADR 0001 (доверенный заголовок `X-User-Id`) и ADR 0002 (асинхронный provisioning через outbox).
- Сессия заканчивается, когда открытых вопросов не осталось и вы подтвердили общее понимание.

В этом проекте понадобились три раунда, примерно 25 решений.

### Шаг 3. PRD: `docs/prd.md` (`/to-spec`)

Согласованная модель оформляется в документ:

- бизнес-правила `BR-01…BR-30`, каждое можно проверить;
- жизненный цикл в виде диаграммы статусов;
- таблица API: возможность, endpoint и кто может её вызвать;
- что не входит в scope (явный список);
- допущения `A-NN`.

Всё, что агент добавил сам, а не согласовал в сессии, он отдельно показывает на подтверждение.

### Шаг 4. Тикеты: GitHub Issues (`/to-tickets`)

- Каждый issue — **вертикальный срез** через все слои (БД, домен, API, тесты), который можно проверить отдельно и который помещается в одну сессию агента.
- Критерии приёмки — чек-лист со ссылками на `BR-NN`.
- Каждый issue явно перечисляет, что в него **не** входит.
- Зависимости заводятся нативными связями GitHub (`blocked_by`). Брать можно только issue без открытых блокеров.

### Шаг 5. Реализация: одна сессия на один issue

```text
/clear  →  /implement #N  →  PR (Closes #N)  →  ревью человеком  →  merge  →  /clear
```

По `AGENTS.md` агент:

1. Читает issue, нужные места PRD и ADR, а также код, который уже есть.
2. Излагает допущения и короткий план. Если нужно решение человека, останавливается.
3. Работает по TDD. Тесты интеграционные, на настоящем PostgreSQL через Testcontainers.
4. Запускает сборку и полный набор тестов, сверяет результат с каждым критерием приёмки.
5. Делает `/code-review` (входит в `/implement`).
6. Создаёт ветку `feature/<issue>-<slug>`, открывает PR с `Closes #N` и таблицей «критерий → доказательство», обновляет `docs/progress.md`.

### Когда агент останавливается и спрашивает

Решения в этом проекте, которые принял человек, а не агент:

- новые зависимости: Testcontainers, xUnit;
- архитектурные границы: отдельный проект на модуль, один общий `DbContext`;
- безопасность: пароль БД вынесен в `.env` и user-secrets, потому что репозиторий публичный;
- любые бизнес-правила, которых нет в PRD.

### Советы по экономии токенов

- **Новая сессия на каждый issue.** Весь контекст живёт в репозитории: `AGENTS.md`, `GLOSSARY.md`, PRD, ADR, issue. Пересказывать предысторию не нужно.
- **Не запускать `/to-spec` и `/to-tickets` повторно для уже нарезанной работы**, иначе появятся дубли. Они нужны только для новой функциональности.
- **Тихие команды:** `dotnet build -v q`, `dotnet test -v q --logger "console;verbosity=minimal"`.
- **Модель под задачу:** Sonnet для простых срезов, Opus для конкурентности, outbox и повторов.
- **Не делать двойное ревью:** `/code-review` уже входит в `/implement`.

### Подготовка окружения (один раз)

- `gh auth login`. После установки `git` или `gh` VS Code нужно закрыть **полностью**, иначе он не увидит новый PATH.
- Нужен запущенный Docker: на нём работают тесты и локальный PostgreSQL.
- Секреты нельзя класть в репозиторий: `.env` в `.gitignore`, строка подключения хранится в `dotnet user-secrets` (см. «Локальный запуск»).
- В Windows PowerShell 5.1 многострочные сообщения для `git commit` и `gh` передаются через Bash heredoc или `--body-file`.
